# 1. 分集解析以客户端为唯一权威

- 状态：Accepted
- 日期：2026-11-21

## 背景

上游 MacCMS 详情接口把分集编码在 `vod_play_url` 里（`线路$$$集名$地址#集名$地址…`）。项目里同时存在两份解析：后端 `/api/detail` 的 `episodes` 字段（平铺、不去重）与前端 `parseEpisodes`（按集名去重、m3u8 优先）。前端实际用的是自己那份，后端算出的 `episodes` 没有消费者，却让响应体膨胀约 141%，并被写进 IndexedDB 缓存。此外还有 `/api/play` 按集名重新解析一次作为兜底。

领域规则是「一个采集站只有一个 m3u8 可播放源」，这条规则目前只活在前端约 20 行的解析函数里。

## 决策

分集解析只发生在客户端。后端不再解析 `vod_play_url`：不返回 `episodes` 字段，也不提供按集名取地址的 `/api/play`（连带 `ProxyPlay` / `ParsePlaylist` / `PlayEpisode` 一并删除）。前端 `parseEpisodes` 是唯一实现，负责「按集名去重 + m3u8 优先」。

## 后果

- 服务端每次详情请求省掉一次解析，响应体减少约 26%（只回传上游原始串），IndexedDB 不再存无人消费的重复数据。
- 解析规则仍然只有 TypeScript 测试守着，Go 侧没有对应测试；改动上游格式时需同步检查前端测试。
- `/api/play` 的既有兜底路径已替换为显式失败提示（`useEpisodeNav` 遇到空 URL 时 toast 提示上游数据异常），不再有服务端二次解析。
- **落地时额外修复了一个真实 bug**：原 `parseEpisodes` 的覆盖条件只看「新 URL 含 `.m3u8`」，导致同一集有两条 m3u8 线路时后一条覆盖前一条，默认线路漂移。已改为「仅当旧值非 m3u8 时才升级」，并由新增单测钉住。这验证了「把唯一真相 + 测试放在一起」的价值。
- 该决策与「便宜的计算放在客户端」的取舍一致：服务端省的是每个用户每次详情页的 CPU 与流量，客户端多付的是一次每个详情页仅执行一次、且可缓存的解析。
